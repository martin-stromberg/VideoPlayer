## 🔴 KRITISCHE PROBLEME (Sofortiger Handlungsbedarf)

### K1 – Hardcodiertes SFTP-Passwort im Quellcode => Erledigt!
**Datei:** `VideoPlayer.Research/Program.cs`, Zeilen 9–18

```csharp
new SFTPMediaSource()
{
    Servername = "***********************",
    Port = **,
    Username = "********",
    Password = "********",
    RootPath = "/"
}
```

**Risiko:** Das Passwort ist im Git-Verlauf gespeichert und für jeden Repository-Zugriff sichtbar.  
**Empfehlung:** Passwort sofort rotieren. Credentials über Umgebungsvariablen oder User Secrets (`dotnet user-secrets`) konfigurieren. Sofern es sich um einen SSH-Server handelt: Key-Based Authentication verwenden.

### K3 – Klartext-Credential-Speicherung in MAUI
**Datei:** `VideoWebPlayer.Maui/Services/AuthService.cs`, Zeilen 28–36

```csharp
Preferences.Default.Get(UserKey, string.Empty)     // Benutzername im Klartext
Preferences.Default.Get(PasswordKey, string.Empty) // Passwort im Klartext
```

**Risiko:** Auf gerooteten Geräten oder über ADB-Backups sind die Credentials auslesbar.  
**Empfehlung:** `SecureStorage` statt `Preferences` für sensible Daten verwenden:

```csharp
// Statt Preferences:
await SecureStorage.Default.SetAsync(PasswordKey, password);
var password = await SecureStorage.Default.GetAsync(PasswordKey);
```

### K4 – Fehlende Authentifizierung in WebPlayerApi
**Datei:** `WebPlayerApi/Program.cs`

**Status:** Historischer Befund zu einem inzwischen entfernten Altprojekt.

Die API verwendet `UseAuthorization()`, hat aber kein konfiguriertes Authentifizierungsschema. Alle Endpunkte sind ohne Authentifizierung erreichbar – jeder kann Medienquellen anlegen, ändern und löschen.

**Empfehlung:** JWT Bearer Authentication oder API-Key-Middleware vollständig implementieren:

```csharp
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options => { /* ... */ });

// und sicherstellen, dass Controller mit [Authorize] annotiert sind
```

---

### K5 – Blockierender `.Result`-Aufruf im Authentifizierungspfad
Ein `.Result`-Aufruf in einem synchronen Kontext im Hot Path der Authentifizierung kann zu Thread-Pool-Starvation führen, insbesondere unter Last.

**Empfehlung:** Alle Authentifizierungsoperationen vollständig async gestalten:

```csharp
// Statt:
var result = SomeAsyncMethod().Result;

// Besser:
var result = await SomeAsyncMethod();
```

## 🟠 HOHE PRIORITÄT

### H1 – IP-Check-Middleware mit umgehbarem Host-Header
**Datei:** `VideoWebPlayer/Services/LoginIpBlockService.cs` oder zugehörige Middleware

Die IP-Prüfung basiert auf dem `Host`-Header, der vom Client manipuliert werden kann.  
**Empfehlung:** `HttpContext.Connection.RemoteIpAddress` verwenden und auf `null` prüfen:

```csharp
var remoteIp = context.Connection.RemoteIpAddress;
if (remoteIp == null) { /* Anfrage ablehnen oder behandeln */ }
```

---

### H2 – Thread-Safety-Problem in Singleton-Service
Ein Singleton-Service verwendet eine nicht-synchronisierte `List<T>`, auf die aus mehreren Threads zugegriffen wird.

**Empfehlung:** `ConcurrentBag<T>`, `ConcurrentDictionary`, oder explizite `lock`-Statements verwenden:

```csharp
private readonly SemaphoreSlim _lock = new(1, 1);
// oder:
private readonly ConcurrentDictionary<string, ...> _items = new();
```

---

### H3 – Spin-Wait-Anti-Pattern mit `Task.Delay(10)`
Polling-Schleifen mit kurzen Delays (`Task.Delay(10)`) sind ineffizient und können zu Deadlocks führen.

**Empfehlung:** `SemaphoreSlim`, `TaskCompletionSource` oder reaktive Patterns (z. B. `Channel<T>`) verwenden.

---

### H4 – Nicht implementierte Endpunkte werfen `NotImplementedException`
Mehrere API-Endpunkte werfen `NotImplementedException` im Produktionscode.

**Empfehlung:** Nicht fertige Endpunkte entweder vollständig implementieren oder mit `[ApiExplorerSettings(IgnoreApi = true)]` und `return StatusCode(501)` markieren. Niemals `NotImplementedException` in Produktionscode.

---

### H5 – API-Tokens werden vollständig in Logdateien geschrieben
Die Logging-Konfiguration protokolliert Request-Header vollständig, wodurch API-Tokens in den Logs erscheinen.

**Empfehlung:** Sensible Header von der Protokollierung ausschließen:

```csharp
// In der Middleware oder Logging-Konfiguration:
.Filter.ByExcluding(e => e.Properties.ContainsKey("RequestHeader_Authorization"))
```

---

### H6 – Fehlende Fehlerprotokollierung in WebPlayerApi-Controllern
**Datei:** `WebPlayerApi/Controllers/MediaController.cs`, Zeilen 72–89

**Status:** Historischer Befund zu einem inzwischen entfernten Altprojekt.

Exceptions werden gefangen, aber nicht protokolliert:

```csharp
catch (Exception)
{
    return StatusCode(500); // Exception wird verschluckt
}
```

**Empfehlung:**

```csharp
catch (Exception ex)
{
    _logger.LogError(ex, "Fehler bei {Action}", nameof(GetMedia));
    return StatusCode(500);
}
```

**Empfehlung:** `WebPlayerApi` auf .NET 10.0 migrieren, um von aktuellen Performance-Verbesserungen und Security-Fixes zu profitieren und die Long-Term-Support-Version zu nutzen.

## 🟡 MITTLERE PRIORITÄT

### M1 – N+1-Query-Probleme
Beim Laden von „Zuletzt angesehen" und „Weiterschauen"-Einträgen werden Einzelabfragen in Schleifen ausgeführt statt einer einzigen Bulk-Abfrage.

**Empfehlung:** `.Include()` in EF Core verwenden oder Daten mit einem einzigen Query laden:

```csharp
// Statt:
foreach (var item in items) { var details = await _db.GetDetails(item.Id); }

// Besser:
var itemsWithDetails = await _db.Items
    .Include(i => i.Details)
    .ToListAsync();
```

---

### M2 – Client-seitiges Paging nach vollständigem Datenladen
Daten werden vollständig vom Server geladen und dann clientseitig paginiert, anstatt serverseitiges Paging zu nutzen.

**Status:** Der Verweis auf `WebPlayerApi.Common` ist historisch; das Altprojekt wurde entfernt.

**Empfehlung:** Paging-Parameter (`page`, `pageSize`) in API-Endpunkte einbauen und `PagedResult<T>` (bereits in `WebPlayerApi.Common` vorhanden) konsequent einsetzen.

---

### M3 – Fehlende Eingabevalidierung in API-Endpunkten
API-Endpunkte prüfen eingehende Daten nicht vollständig (z. B. fehlende `[Required]`-Attribute, keine Model-Validation).

**Empfehlung:** FluentValidation oder DataAnnotations konsequent einsetzen:

```csharp
builder.Services.AddControllers()
    .ConfigureApiBehaviorOptions(opt =>
        opt.InvalidModelStateResponseFactory = /* custom factory */);
```

---

### M4 – Pfad-Vergleichsfehler (Logikfehler)
In einer Service-Methode wird ein Pfad mit dem Passwort statt mit dem korrekten Pfad verglichen. Dies ist ein potenzieller Logikfehler.

**Empfehlung:** Betroffene Vergleichslogik prüfen und Einheitstests für Pfadvergleiche hinzufügen.

---

### M5 – Detaillierte Fehlermeldungen in Produktion aktiviert
In der Blazor-App ist `DetailedErrors` möglicherweise auch in Produktionsumgebungen aktiv, was interne Implementierungsdetails preisgibt.

**Empfehlung:** `DetailedErrors` ausschließlich für `Development` aktivieren:

```csharp
if (builder.Environment.IsDevelopment())
{
    builder.Services.AddServerSideBlazor().AddCircuitOptions(o => o.DetailedErrors = true);
}
```

---

### M6 – Unzureichende Test-Abdeckung in VideoWebPlayer.Maui.Tests
Das MAUI-Testprojekt enthält nur eine einzige Testdatei (`ContinueWatchingEventIngressTests.cs`). Wesentliche Services wie `AuthService` oder `VideoWebPlayerClient` haben keine Tests.

**Empfehlung:** Tests für mindestens folgende Bereiche hinzufügen:
- `AuthService` (Login, Token-Speicherung, Logout)
- `VideoWebPlayerClient` (HTTP-Fehlerbehandlung, Retry-Logik)
- Navigation und State-Management

---

### M7 – SFTP-Verbindungsmanagement ohne using/Disposing-Garantie
**Datei:** `VideoWebPlayer/Services/SftpMediaSourceReader.cs`

Ressourcen werden möglicherweise nicht zuverlässig freigegeben, wenn Exceptions auftreten.

**Empfehlung:** `using`-Statements sicherstellen:

```csharp
await using var client = new SftpClient(host, port, user, password);
```

---

### M8 – Magic Strings für Konfigurationsschlüssel
Konfigurationsschlüssel werden als hardcodierte Strings übergeben, ohne zentrale Konstanten.

**Empfehlung:** Konfigurationsschlüssel in statische Klassen auslagern:

```csharp
public static class ConfigKeys
{
    public const string ApiBaseUrl = "Api:BaseUrl";
    public const string AllowedOrigins = "Cors:AllowedOrigins";
}
```

## 🔵 NIEDRIGE PRIORITÄT / TECHNISCHE SCHULDEN

### N1 – Veraltetes `VideoPlayer.Research`-Projekt
Das Research-Projekt enthält Wegwerf-Code (u. a. hardcodierte Credentials) und sollte nicht im Haupt-Repository bleiben.

**Empfehlung:** In ein separates, privates Repository verschieben oder vollständig entfernen. Mindestens: alle Credentials entfernen und das Projekt aus dem Release-Build ausschließen.

---

### N2 – Fehlende XML-Dokumentation für öffentliche APIs
Öffentliche Klassen und Methoden in `WebPlayerApi.Common` und den Controllern haben keine XML-Dokumentationskommentare.

**Status:** Historischer Befund zu einem inzwischen entfernten Altprojekt.

**Empfehlung:** Zumindest für Controller-Aktionen und öffentliche DTOs XML-Dokumentation hinzufügen – verbessert die automatisch generierte OpenAPI/Swagger-Dokumentation.

---

### N3 – Blazor-Server und WASM-Client als separate Projekte ohne klare Abgrenzung
Die Aufteilung zwischen `VideoWebPlayer` (Server) und `VideoWebPlayer.Client` (WASM) ist in Teilen unklar.

**Empfehlung:** Die Verantwortlichkeiten klar dokumentieren: Was wird serverseitig gerendert, was läuft im Browser?

---

### N4 – `build_script.bat` ohne Fehlerbehandlung
Das Build-Skript bricht bei Fehlern nicht ab (`echo` ohne `exit /b`).

**Empfehlung:** `@echo off` und `if errorlevel 1 exit /b 1` nach kritischen Build-Schritten einfügen.

---

### N5 – Inkonsistente Namenskonventionen
In einigen Bereichen werden verschiedene Konventionen gemischt (z. B. `DtoSource` vs. `MediaItemDto`).

**Empfehlung:** Einheitliche Namenskonvention für DTOs festlegen (z. B. immer Suffix `Dto`).

---

### N6 – Fehlende `CancellationToken`-Weitergabe
Mehrere async-Methoden nehmen keinen `CancellationToken`-Parameter entgegen, obwohl dies in HTTP-Handlern Standard sein sollte.

**Empfehlung:** `CancellationToken cancellationToken = default` zu allen relevanten async-Methoden hinzufügen und an EF Core / HttpClient weitergeben.

---

### N7 – `Pages/`-Verzeichnis und `Program.cs` im Root-Verzeichnis
Im Repository-Root befinden sich `Pages/`, `Program.cs` und `wwwroot/` – wahrscheinlich Überreste eines früheren Projekts.

**Empfehlung:** Diese Dateien entfernen oder in das korrekte Projekt verschieben.

---

### N8 – `.gitignore` deckt nicht alle sensiblen Dateien ab
Obwohl `appsettings.Development.json` und Datenbankdateien ausgeschlossen sind, fehlen möglicherweise weitere sensible Pfade (z. B. lokale Publish-Ausgaben).

**Empfehlung:** `.gitignore` um folgende Einträge erweitern:
```
Publish/
**/publish/
*.pfx
*.p12
```
