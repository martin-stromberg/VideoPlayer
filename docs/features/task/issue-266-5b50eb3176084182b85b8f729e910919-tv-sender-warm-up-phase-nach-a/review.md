## Hinweise

- Die Tasks-Datei wurde vollständig überschrieben; alle 26 Aufgaben stehen auf `Erledigt` mit konkretem Testnachweis (Datei:Zeile).
- **Dokumentierte Planabweichung (Task 19):** Der Plan verlangt wörtlich „`#live-tv-stream-error` erscheint nicht". Headless-Chromium kann die Standby-Segmente (H.264/AAC) nicht decodieren — ein codec-bedingter Fehlerhinweis wäre auch beim echten Stream erwartbar. Umsetzung: Der Hinweis darf zum Zeitpunkt der ersten Standby-Playlist-200 nicht existieren (dominiert alle Lieferfehler, die synchron zum Playlist-Laden auftreten); erscheint er später, muss die Fehlerart codec-seitig sein. Die Begründung steht als Entscheidungskommentar im Test (Z. 221-241) — entspricht der in `review.1.md` genannten Alternative „Planabweichung explizit als Entscheidung dokumentieren".
- **Kleine Änderung außerhalb des Plans:** `LiveTv.razor` erhielt ein unsichtbares Diagnose-Attribut `data-error-kind` (Z. 74) samt `streamErrorKind`-Feld, das `NotifyStreamError(kind)` befüllt — nötig, damit der E2E-Test Lieferfehler von Codec-Fehlern unterscheiden kann. Keine sichtbare UI-Änderung; `liveTv.js` unverändert (der `kind`-Parameter existierte bereits).
- Build-/Testlauf-Nachweise (Task 21, 25) wurden auch in dieser Runde nicht erneut ausgeführt — geprüft wurde das Vorhandensein von Implementierung und Tests im Code.
- `PrepareAsync` ist `internal` (statt `public`) — konsistent mit der Test-Seam-Designentscheidung (`InternalsVisibleTo` gesetzt).
- Über den Plan hinaus umgesetzt (positiv): Transcode-Timeout + Pump-Drain gegen stallende Inputs im Segmenter, Cache-Invalidierung per Quell-Änderungsstempel, Rückfall auf den Default bei gelöschtem MediaItem trotz Cache-Marker, Catch-All-Fehlpfad mit `_failedMediaItemId` (Retry-Sturm-Schutz) — jeweils durch die drei zusätzlichen Provider-/Segmenter-Tests abgesichert.
