## Hinweise

- **`Kestrel:Limits:MaxRequestBodySize` wird aus `appsettings` nicht gebunden:** Der `KestrelConfigurationLoader` lädt aus der `Kestrel`-Sektion nur `Endpoints`/`EndpointDefaults`/Zertifikate — `Limits` bleibt ungelesen (verifiziert an der aktuellen Kestrel-Quelle und Microsoft-Doku: Limits sind via `builder.WebHost.ConfigureKestrel(o => o.Limits.…)` in Code zu setzen; bekannte Einschränkung, dotnet/aspnetcore#37544). Der geplante Konfigurationseintrag (und die alternative Umgebungsvariable) ist daher wirkungslos. Funktional unproblematisch, weil `[DisableRequestSizeLimit]` das Limit per Request über `IHttpMaxRequestBodySizeFeature` aufhebt und unter IIS-OutOfProcess das Kestrel-Limit ohnehin durch ANCM deaktiviert ist — aber die Planbegründung „kein serverseitiges Größenlimit greift durch die Konfiguration" trifft nicht zu. Falls ein konfigurationsgesteuertes Limit gewünscht ist, wäre `ConfigureKestrel(o => o.Limits.MaxRequestBodySize = null)` nötig; der Wert `0` wäre bei tatsächlicher Bindung zudem falsch (`null` = unbegrenzt, `0` = 0 Bytes).
- **`AppendChunkAsync`-Zugehörigkeit inkonsistent:** Der Programmablauf ruft `session.AppendChunkAsync(Request.Body, …)` auf, die „Neue Klassen"-Tabelle führt die Methode dagegen beim `BackupUploadSessionService`. Kosmetisch — bei der Implementierung zu klären (Session-Methode nahe am `SemaphoreSlim`/`FileStream` liegt näher).
- **`PersistentComponentState`-Token nur beim Prerender-Übergang:** `TryTakeFromJson("antiforgeryToken")` liefert nur beim Übergang Prerender→Interactive einen Wert; bei In-Circuit-Navigation zwischen interaktiven Admin-Seiten ist der Zustand leer und `IHttpContextAccessor.HttpContext` weiterhin `null` → `antiforgeryRequestToken` = `null` → `StartUploadAsync` meldet den geplanten Fehler. Diese Einschränkung besteht im übernommenen `Updates.razor`-Muster bereits und ist nicht neu eingeführt — ggf. bei Implementierung mitbedenken (z. B. Full-Reload-Navigation im Admin-Bereich oder Token-Nachforderung).
- Ein expliziter negativer Antiforgery-Test (Chunk-Request ohne/ungültiges Token → 400) ist weiterhin nicht geplant; die Prüfung wird implizit über den Happy-Path-E2E mitabgedeckt. Optional ergänzbar.
