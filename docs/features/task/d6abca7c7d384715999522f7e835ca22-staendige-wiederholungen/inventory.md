# Bestandsaufnahme: Ständige Wiederholungen — faire Strang-Rotation bei der Interleaved-Ausstrahlungsbelegung

Analysiert wurde die Strang-Belegung des automatischen Sendeplans (`ProgramScheduleService` und angrenzende Bausteine) bezogen auf die Anforderung in `requirement.md`: Der Startstrang der Round-Robin-Belegung interleaveter Regeln (`SelectAiringItemsInterleaved`) soll über aufeinanderfolgende Ausstrahlungen rotieren, statt jede Ausstrahlung bei Strang 0 der `StrandOrderKey`-Reihenfolge zu beginnen.

## Zusammenfassung

- **Fehlerursache im Code bestätigt:** `StrandStartOffset` (`ProgramScheduleService.cs:1421`) liefert die Tagesrotation nur bei `wanted < strandCount`. Bei `SlotDuration`-Regeln ist `wanted = int.MaxValue` (`SelectAiringItemsInterleaved`, Z. 1811–1812), der Offset also stets 0 — jede Ausstrahlung startet beim ersten Strang der festen `StrandOrderKey`-Reihenfolge.
- **Verstärkende Faktoren im Ist-Stand:** Seit Issue #334 bildet jede Filmsammlung einen eigenen geordneten Strang `collection:{id}` (`TryMovieItem`, Z. 2299–2305). Die Clip-Grace (`RuleState.ClipGrace`, Z. 1279–1281; Abbruch in `SelectAiringItemsInterleaved`, Z. 1844–1848) beendet die Titel-Auswahl bei `target - accumulated < PlaceholderGrace` — bei ~110-min-Filmen und 15 min Grace typischerweise nach zwei Titeln. Kombination: Es werden nur die ersten zwei nicht-leeren Stränge je Ausstrahlung bedient, jede Ausstrahlung dieselben.
- **Genau zwei Aufrufpfade, ein gemeinsamer Codepunkt:** `SelectAiringItemsInterleaved` wird ausschließlich über `SelectItems` (Z. 1773) erreicht — von `MaterializeOccurrence` (`EnsureCoverageAsync`, Z. 1674) und `MaterializeOccurrenceEvicting` (`ReconcileAsync`, Z. 1102). Eine Korrektur an der einen Stelle hält beide Pfade konsistent. Kein weiterer Pfad (Diagnose, Vorschau, UI) nutzt die Strang-Auswahl: `GetRuleDiagnosesAsync` expandiert nur Material, die Admin-Seite ruft keine Planungsschritte direkt auf, produktiv läuft alles über `ExecutePassAsync` im `ProgramScheduleWorker`.
- **Re-Bewertung ist pick-reihenfolge-agnostisch (zentrale Antwort auf die offene Frage):** `ReconcileWindow.Validate`/`SlotStillValid` prüft je Slot nur Mitgliedschaft in der Expansion, geschriebene Laufzeit, Altersfenster und — bei geordneten Strängen — Ring-Kontiguität innerhalb der Gruppe. Die Strang-Pick-Reihenfolge bzw. der Startstrang einer Ausstrahlung wird nicht geprüft (`lastIndex`-Baseline je Strang/Gruppe ist ungeprüft, Z. 737–744). Folgerung in beide Richtungen: (a) Eine rotierte Belegung erzeugt **keine** Fehlinvalidierungen korrekt geplanter Ausstrahlungen; (b) bereits mit Offset-0-Logik geschriebene, fachlich gültige Zukunftsslots validieren auch nach der Korrektur weiter als gültig — die issue-seitig erwartete Selbstheilung („falsch belegte Tage werden ersetzt") ist durch den bestehenden Validierungsmechanismus allein **nicht** abgedeckt und bedarf einer eigenen Entscheidung im Umsetzungsplan.
- **Rotationsanker-Fakten:** `StrandStartOffset` arbeitet auf `airingStartUtc` — dem realen, möglichst verschobenen Start (`ShiftPastInvaders`), nicht dem nominalen Occurrence-Start — und nimmt dessen **UTC-Datum** (`startUtc.Date - UnixEpoch`). Ein über Mitternacht (UTC) geschobener Start landet auf einem anderen Rotationstag; Coverage- und Reconcile-Materialisierung können für dieselbe Occurrence unterschiedliche `airingStart`s (und damit Offsets) sehen.
- **Bestehende Tests, die das Ist-Verhalten festnageln:** `ProgramScheduleServiceTests_PrimetimeRolling.EnsureCoverage_WeekOfAirings_StrandStructureStableAndOrderContinues` (identische Titel-Typ-Sequenz jeden Abend) und `ProgramScheduleServiceTests_Interleaving.EnsureCoverage_GenreRule_InterleavesShows_StableSlotsAcrossDays` / `..._LeadStrand_FollowsHashOrder_NotAlphabetic` kodieren „stabile Strang-Position über Tage" — je nach gewählter Rotationsbedingung anzupassen.
- **Kein Datenmodell-/Interface-/Enum-/UI-Eingriff nötig:** `ProgramRuleCursors` tragen die Strang-Cursor (`StrandKey`, eindeutig gefilterter Index); `StrandState`, `CommitScan`, `PersistCursors`, `RewindRing` sind strandbezogen und rotationsneutral.
- **Test-Ausgangszustand:** Baseline `dotnet test -c Release --filter "Category!=E2E"` am 2026-11-07 (Commit `3b2a616`): **2665 Tests — 2664 bestanden, 1 übersprungen (plattformbedingt, Unix-only), 0 fehlgeschlagen**; Details und Nachweise in [inventory/tests.md](inventory/tests.md).
